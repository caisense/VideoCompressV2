/goal

# VideoCompress 新增 GAN 模式
# 8 / 10 / 12 fps H.265 + Full-frame Real-ESRNet / Real-ESRGAN A/B
#
# 核心目标：
#
# 在完全保留现有 rebuild 模式的前提下，
# 新增一个独立 `gan` 模式：
#
# RK3588：
#
#     Camera
#       ↓
#     YOLOv8-Seg
#       ↓
#     semantic ROI/QP map
#       ↓
#     H.265 only
#     256×144 @ 8/10/12fps
#       ↓
#     <=100kbps shared physical link
#
# PC：
#
#     H.265 decode
#       ↓
#     full-frame enhancer
#       ├─ NONE / Lanczos baseline
#       ├─ Real-ESRNet x2
#       └─ Real-ESRGAN x2
#       ↓
#     512×288
#       ↓
#     resize
#       ↓
#     640×360
#
#
# GAN 模式必须完全不依赖：
#
#     RB/1 rebuild STATE
#     reference JPEG
#     reference generation
#     segmentation reference mask
#     FEC PATCH
#     ROI paste
#     content registration
#     reference AGE
#     SR handover
#
# YOLO 仍保留，
# 但只负责：
#
#     “编码时哪里应该获得更多 bit”
#
# 不再负责：
#
#     “接收端哪里应该贴高质量图像”
#
#
# 最终通过：
#
#     8 / 10 / 12 fps
#          ×
#     NONE / ESRNet / ESRGAN
#
# 做完整 A/B，
# 找到 RTX 3060 Laptop 6GB + 100kbps 链路下
# 在：
#
#     人脸清晰度
#     多目标稳定性
#     temporal flicker
#     GPU latency
#     H.265质量
#     总链路延迟
#
# 之间的最佳工程点。

======================================================================

这是强制要求。

现有：

    baseline
    low
    rebuild

等已有 mode / profile 行为必须保持兼容。

新增：

    gan

不能直接把：

    rebuild

重命名或改写成 full-frame GAN。


必须可以：

    --mode=rebuild

继续运行当前逻辑。


同时：

    --mode=gan

运行新的 H265-only + PC full-frame enhancement。


======================================================================
2. GAN 模式的架构边界
======================================================================

GAN mode sender：

允许：

    Camera
    YOLOv8-Seg
    tracker（如果编码 ROI/QP 需要）
    ROI/QP map
    MPP H265
    RTP
    audio

禁止：

    rebuild STATE
    reference JPEG
    reference mask
    reference FEC
    RB/1 side channel
    rebuild sender
    reference refresh scheduler


也就是说：

GAN mode 网络侧只传：

    H265
    +
    audio（如启用）


不要因为代码复用方便：

继续后台发送 STATE/PATCH。


验收：

GAN模式：

    RB bitrate = 0
    PATCH packet count = 0
    STATE packet count = 0


======================================================================
3. GAN 模式仍然使用 YOLO ROI/QP
======================================================================

不要把 GAN mode 简化为：

    uniform H265


保留当前已经存在的：

    YOLOv8-Seg
        ↓
    RoiMap / QP map
        ↓
    MPP H265 ROI regions


核心思想：

同样的 H265 bitrate：

    person / vehicle
        → lower QP
        → preserve more real information

    background
        → higher QP
        → stronger compression


最终：

    semantic encoding
    +
    uniform full-frame restoration


这是 GAN mode 的主架构。

======================================================================

在现有配置系统中增加：

    mode = GAN

或者与当前项目命名风格一致的：

    PIPELINE_GAN

    --profile=gan8

优先：

======================================================================
5. GAN 模式帧率必须真实改变采集/编码节奏
======================================================================

不能只：

    HUD显示10fps

而 camera / inference / H265 实际还是6fps。


检查：

    CameraCapture
    inference scheduler
    encoder fps
    RTP timestamp
    GOP
    IDR cadence

    实际产生约8个独立H265 source frame/s

    约10fps


gan-fps=12：

    约12fps


接收端统计：

    unique decoded source FPS

不能把 HOLD frame 算进去。


======================================================================
6. GAN 模式不做6→12 HOLD作为主输出
======================================================================

当前 rebuild：

    6fps source
    →12fps HOLD


GAN模式：

如果输入：

    8fps

默认输出：

    8个真实增强帧/s


输入：

    10fps

输出：

    10个真实增强帧/s


输入：

    12fps

输出：

    12个真实增强帧/s


如果 UI 层需要：

    16 / 20 / 24Hz

可做 display HOLD，

但必须明确：

    SOURCE FPS
    ENHANCED FPS
    DISPLAY FPS

三个概念。


不要把 display HOLD
冒充真实增强fps。


======================================================================
7. 100kbps 仍是绝对硬限制
======================================================================

GAN模式不得修改：

    global physical link cap = 100000 bps


如果有音频：

100kbps包括：

    H265
    audio
    RTP/UDP相关现有budget定义


必须沿用当前项目对：

    LINK CAP

的实际定义。


GAN mode 没有 RB/PATCH 后，

原本 rebuild side-channel 占用的码率：

优先重新分配给：

    H265


但不能：

    因为RB=0
    就直接把H265设成100kbps

必须给：

    audio
    protocol
    pacing margin

留预算。

8. 新增可配置 H265 bitrate
======================================================================

增加：

推荐初始测试：

    80

自动留预算。

默认：

例如：

100kbps link：

    H265 target ≈ 70~80kbps


最终值由真机 wire telemetry 决定。

======================================================================
10. 编码 FPS 与每帧 bit 的关系必须记录
======================================================================

    ≈9375 bit/frame

10fps：

    ≈7500 bit/frame

12fps：

    ≈6250 bit/frame

    frame bytes
    I-frame bytes
    P-frame bytes
    average bits/frame


A/B报告必须包含。

作为主要设计语义。

在8/10/12fps基本一致。


======================================================================
12. YOLO inference FPS
======================================================================

不要默认 YOLO 必须等于视频fps。


首先测 RK3588 当前 YOLO 实际性能。


提供配置：

    --gan-inference-fps


默认策略：

A.

如果 YOLO >= source fps：

    inference every frame


B.

如果12fps视频时NPU跟不上：

    inference 6fps
    ROI/QP map between detections reuse / track


例如：

video 12fps
YOLO 6fps

    detection
    reuse
    detection
    reuse


不要因为提高视频fps：

让整个 pipeline 被 YOLO 阻塞。


======================================================================
13. ROI/QP map 必须时间连续
======================================================================

要求：

    人脸清晰

    ROI全部消失


导致 H265 自己产生周期性质量闪烁。

======================================================================
22. 推理队列必须 latest-frame-only
======================================================================

这是非常重要的。


如果 enhancer 推理速度 < input fps：

禁止：

    frame1
    frame2
    frame3
    frame4
    ...

无限排队。


否则：

视频越来越延迟。


设计：

    at most 1 running
    +
    1 latest pending


新的 pending 到来：

覆盖旧 pending。


即：

    RUN=1
    Q<=1


与当前 SR latest-only 思路一致。


======================================================================
23. Full-frame增强的 source-frame immutable
======================================================================

每个 decoded source frame：

只能产生一次最终 enhanced output。


不得：

先显示Lanczos
↓
稍后GAN完成
↓
再修改同一frame


如果 GAN 没及时完成：

有两种策略。


默认：

    wait within latency budget


超过预算：

    DROP source frame
    使用最新完成 enhanced frame


不要在同一个 source identity 上：

Lanczos → GAN

造成质量跳变。

======================================================================
44. Temporal stability 是核心指标
======================================================================

不能只看：

单帧截图。


必须统计：

同一个 face / person ROI
连续时间上的：

    sharpness variance
    brightness variance
    temporal difference


至少实现：

Laplacian variance
per frame


然后计算：

    mean
    std
    coefficient of variation


Sharpness CV：

    std(sharpness)
    /
    mean(sharpness)


值越低：

锐度越稳定。


======================================================================
45. Temporal flicker metric
======================================================================

增加一个简单但有用的指标。


相邻帧：

先做：

    global / local motion compensation（如果已有）


或至少：

    resize/aligned ROI


计算：

    abs(frame_t - frame_t-1)


然后：

排除合理运动区域后
统计高频残差。


如果实现复杂：

先使用：

    temporal LPIPS（若已有依赖）

或：

    ROI intensity/edge variance


不要为了一个指标
引入大型新框架。
