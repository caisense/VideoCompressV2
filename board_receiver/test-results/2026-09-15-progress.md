## Findings and fixes

- The board MPP runtime crashed in `mpp_destroy -> h265d_deinit` during the
  first profile change. GDB showed stale HEVC reference-slot teardown. Calling
  `MppApi::reset` before `mpp_destroy` fixed repeated decoder recreation and
  clean SIGTERM shutdown.
- MPP compressed input memory must remain alive after queue acceptance. The
  receiver now keeps a bounded 256-AU ownership queue and releases input as
  decoded frames return.
- Existing sender defaults use a three-frame/250 ms send queue. A paced
  high-profile IDR alone can exceed 250 ms, causing avoidable recovery drops.
  Existing supported options `--send-queue-frames=16` and
  `--send-max-latency-ms=2000` prevent those drops without changing source or
  wire protocol; a clean high run then remained at zero MPP errors.

## Commands used for the 2026-09-16 checks

The receiver-late test used the README sender command with
`--rate-profile=medium`, `--send-queue-frames=16`, and
`--send-max-latency-ms=2000`. Board 101 was then started with:

```sh
env XDG_RUNTIME_DIR=/run WAYLAND_DISPLAY=wayland-0 \
  ./board_h265_receiver --udp-port=5004 --display=wayland --fullscreen \
  --rotate=ccw --receive-buffer-bytes=1048576 --reorder-window=32 \
  --stats-interval-ms=1000
```

The fault-injection receiver command was:

```sh
./board_h265_receiver --udp-port=5004 --headless --reorder-window=4 \
  --stats-interval-ms=500 --idle-timeout-ms=3000
```

The injected RTP packets used PT 96 and valid RO v1 metadata. Sequence order
was `100, 102, 101, 102, 108, 109, 111, 112, 113, 114`; 109/111 formed an
incomplete FU pair and the final three packets used profiles 3, 4, and 99.
